# 【Unity(KMX)側 要望・不具合報告】/kmx/attached のヘッド各箱の pose が時々 (0,0,0) で送られる

**方向：ROS2側 → Unity側**（受信・調査は Unity 担当）。**間引きヘッド（headAsSingleBox=false で複数箱送信）**運用で、
**時々（間欠的に）ヘッド全体が手首(flange)原点に潰れて表示される**不具合。原因は **Unity が各箱の pose を (0,0,0) で送っている**こと。

---

## 0. 症状
- ROS2 の planning scene に attach されたヘッド11箱を確認すると、**全箱の pose が pos=(0,0,0)・orientation=単位（rpy 0,0,0）**。寸法(dimensions)は正しい。
- ＝ヘッド全体が **flange 原点の一点に潰れて**いる（＝「変な位置」の正体）。
- **時々発生**（毎回ではない）＝一過性のタイミング/初期化レースを示唆。

### 実測（ROS2 側 GetPlanningScene）
```
attached count = 11
[FANUCヘッド#hc0]  pos=(0,0,0) rpy=(0,0,0) dim=[0.268,0.2,0.183]
[FANUCヘッド#hc1]  pos=(0,0,0) rpy=(0,0,0) dim=[0.33,0.197,0.354]
... 全11箱すべて pos=(0,0,0) ...
位置レンジ x[0,0] y[0,0] z[0,0]     ← 全箱が原点に集中
```

## 1. これは Unity 側の送信内容の問題（切り分け済み）
- ROS2 側は受信した各箱 pose に **`head_calibration_rpy`(=[0,90,90]) の回転を掛けるだけ**（[[HEAD_TOOL_ROS2_SPEC]] §B / HANDOFF §4.1）。
- 回転は **「ゼロベクトル→ゼロ」にはできるが「非ゼロ→ゼロ」にはできない**。全箱がきっかり (0,0,0) ＝ **Unity が pose=(0,0,0) で送信している**確定的証拠。
- 寸法は正しく届いている＝**位置/向きの計算だけが時々ゼロになる**。ROS2 は忠実に反映しているだけ。

## 2. 契約（再確認・ここは変えない）
`/kmx/attached`(kmx_msgs/Obstacles) の各 `ObstaclePrimitive`：
- `pose` = **attach 先リンク（flange）相対**の位置＋向き。**メートル・ROS(FLU)・raw**（向き補正は ROS2 の `head_calibration_rpy` が担当＝Unity は生で送る。二重補正禁止）。
- `dimensions` = 箱寸法[m]（現状これは正しく送れている）。
- `id` = 箱ごとの安定 ID（hc0..）。

## 3. 要望（Unity 側の修正）
**各間引き箱の pose（flange 相対の位置＋向き）を、送信前に確実に有効値で確定させる。** 具体的には：
1. **transform 準備前に取得していないか確認**：Send Head 実行時、ヘッド各コライダーの「flange 相対」変換が有効か。Play 開始直後・シーン再構築直後・ロボットが動作中など、**変換がまだ確定していないフレームで pose を取ると原点(0)/単位になる**ことがある。
2. **縮退ガード**：計算した pose が全て (0,0,0)（または flange 変換が無効）なら **送信しない／再計算する**。
3. **参照フレームの一貫性**：`headAsSingleBox=true`（1箱）では正しく出ていた場合、間引き（複数箱）経路だけの座標計算バグの可能性。1箱経路と同じ「flange 相対」の取り方に揃える。
4. （デバッグ）送信直前に各箱の pose をログ出力し、非ゼロで妥当か確認できるようにする。

## 4. 検証（Unity 修正後）
ROS2 側で以下を確認できれば OK：
```bash
# 各ヘッド箱が flange 相対で「非ゼロ・散らばって」いること（原点集中でない）
python3 <session scratchpad>/dump_attached.py
# または
ros2 service call /get_planning_scene moveit_msgs/srv/GetPlanningScene "{components: {components: 1023}}"
```
- 期待：11箱が pos≠(0,0,0) で、ヘッド形状をなす配置。位置レンジが 0 でなく実寸（〜0.5m 程度）に広がる。

## 5. ROS2 側の保険（別途・任意）
一過性 glitch でシーンが壊れないよう、ROS2 側にも **「受信ヘッドの全 item が pose≒原点なら、その更新を破棄して前回の正常なヘッドを維持」** の防御ガードを追加可能（root cause は Unity 側の pose 計算）。必要なら実装する。

## 7. Unity側 対応（実装済・2026-07-07）
`ComRos2Obstacles.SendHead()` に以下を実装：
- **縮退ガード**：各コライダーの flange 相対中心を集計し、**全箱の中心がフランジ原点付近(<0.1mm)なら「pose 未確定」とみなして送信スキップ**（return false）。→ pose=0 を送らず、ROS2 は前回の正常な attach を維持。
- **オート送信のリトライ**：ロード直後のオート送信(`autoSendOnLoad`)は、ヘッドが縮退で送れないうちは `sentOnce` を確定せず**次回(0.5s後)リトライ**。transform 確定後に正しく送る（上限回数で打ち切り）。
- **送信ログに `nearZero=N`** を追加（再現時に「原点付近の箱数」を可視化）。debugPose では各箱の flange 相対値も出力。
- 所見：pose 計算は 1箱/間引きで**共通**なので「間引き特有」ではなく、**ロード直後のオート送信で transform 未確定フレームを踏むタイミングレース**が主因と推定（縮退ガード＋リトライで根治）。

### ★ROS2側へ再確認したいこと（矛盾点のすり合わせ）
- 不具合時の **pose 生値（丸めなし）と箱数**：本当に「11箱すべて厳密に (0,0,0)」か？
  → Unity 間引きは各箱の中心でグリッド分けするため、**全中心が0なら1箱に潰れる**はず（11箱にならない）。11箱が全0なら、別の潰れ方 or 丸め表示の可能性。生値で確認できると原因が確定します。
- どちらの経路で再現したか（ロード直後のオート送信 / 計画ボタン）。

### §5 について
ROS2側の防御ガード（**受信ヘッドの全 item が pose≒原点なら更新破棄＝前回維持**）は**保険として有用**。両側で守ると一過性 glitch に強くなるので、実装いただけると安心です（root cause は Unity 側で対処済）。

## 8. ROS2側 回答（2026-07-07）
- **矛盾点の解消**：不具合時の11箱は **dimensions が全てバラバラ**（実測 `[0.268,0.2,0.183]`/`[0.33,0.197,0.354]`/`[0.189,0.317,0.182]`…）で、
  **pose だけが全て (0,0,0)**（rpy も 0）でした。＝**グリッド分けは 11 箱に正しく分かれて成立**（各箱の中心/寸法は区別できている）が、
  **送信された flange 相対 pose が全箱 0**。よって「全中心が0→1箱に潰れる」ではなく、**「11箱は正しく分かれたが、各箱の pose を書く/変換する段で 0 になった」**。
  そちらの **「ロード直後のオート送信で transform 未確定フレームを踏む」仮説と整合**します（グリッド分けの寸法は先に確定、pose だけ 0 で送信）。
- **厳密0か微小値か**：ROS2 の dump は位置を**小数3桁に丸めて**表示していたため 0.000 でした（厳密0かは未確定）。**次回ヘッド受信時に丸めなしの生値**を採取して確定します。
  ただし Unity の縮退ガードで送信スキップされると採れないので、**確認したい場合は一時的にガードを外して1回だけ縮退状態を送って**ください（生値 `ros2 topic echo /kmx/attached` で確定できます）。
- **再現経路**：ROS2 側からは判別不可（Unity のどの送信経路か）。ログのタイムスタンプ上はシーン送信時。Unity 側ログ（`nearZero=N`・経路）で確定を。
- **★ROS2 保険ガード＝実装・検証済(2026-07-07)**：`planner_node.py` の `on_attached` 冒頭に
  **「複数 item が全て pose≒原点(<0.1mm) なら更新を破棄し、前回の正常ヘッドを維持」**（空配列=全消しは除外）を追加。sync/build/反映済。
  検証：正常2箱→縮退2箱送信で**前回維持（破棄・警告ログ）**／空配列で**全消し**、を確認。**両側ガードで一過性 glitch に強くなりました**（§5 の依頼に対応）。
